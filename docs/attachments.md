# GoreeCloud Notes Attachment and Inline-Image Model

## Purpose

GoreeCloud Notes treats attachment bytes and note-document references as separate but coordinated data. The design keeps binary storage under GoreeCloud control while preserving a portable application-owned note format.

The Milestone 0 attachment model is deliberately conservative. It supports authenticated file storage, safe raster preview, and attachment-ID-based inline images without allowing arbitrary external image URLs or active document formats to become an implicit rendering surface.

## Storage and Identity

Each attachment has a server-generated UUID and belongs to exactly one user and one note. PostgreSQL stores attachment metadata, including the note relationship, original filename, media type, byte size, SHA-256 checksum, server-generated storage key, and timestamps. Development attachment bytes remain outside ordinary PostgreSQL rows in private GoreeCloud-managed filesystem storage.

Client filenames are metadata only. They are never used as filesystem paths. The storage key is generated by the server and is not exposed as part of the browser document contract.

## Safe Raster Preview Boundary

The authenticated preview endpoint currently permits only this explicit passive-raster allowlist:

- AVIF (`image/avif`)
- GIF (`image/gif`)
- JPEG (`image/jpeg`)
- PNG (`image/png`)
- WebP (`image/webp`)

SVG, HTML, PDF, text, and other non-allowlisted formats remain download-only. An unsupported preview request returns HTTP `415` rather than silently allowing browser rendering of active or unreviewed document content.

Preview responses remain owner-scoped and use `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, and `Cross-Origin-Resource-Policy: same-origin`.

## Native Inline-Image Block

An inline image is represented inside `goreecloud.blocks` version 1 by application-owned data rather than an editor-library URL:

```json
{
  "type": "attachmentImage",
  "attachment_id": "b7b46855-71c0-45ac-9214-29686550ac7c",
  "alt": "Network architecture diagram"
}
```

The stored note does **not** contain a filesystem path, object-storage URL, signed URL, external HTTP URL, or Tiptap-specific image serialization. The browser derives the rendering URL from the authenticated GoreeCloud preview endpoint at runtime.

This boundary is important for portability. A migration or export can preserve the attachment UUID relationship while copying the corresponding binary payload into another approved storage model.

## Server Validation

The backend is authoritative for the document contract. Before saving an inline image, the server verifies that:

1. the document is a supported `goreecloud.blocks` version-1 document;
2. the `attachmentImage` block contains a valid attachment UUID;
3. the referenced attachment belongs to the authenticated user;
4. the referenced attachment belongs to the same note being edited; and
5. the attachment media type is on the approved passive-raster allowlist.

Missing, foreign, wrong-note, or unsupported-media references fail with HTTP `422`. Arbitrary image URLs are not a valid inline-image representation.

The document validator also rejects unknown document versions, unsupported node types, unsupported node placements, unsupported marks, and unknown fields instead of silently discarding content. This protects a note from being partially erased by an older client that does not understand a newer document generation.

## Browser Editing

The Tiptap editor uses a GoreeCloud-owned `attachmentImage` extension. The toolbar can insert an already-uploaded safe raster attachment into the note body. The editor stores only the attachment UUID and alt text in the native document conversion layer.

The rendered `<img>` source is generated from the same-origin authenticated preview endpoint. The UI does not provide a field for arbitrary external image URLs.

The initial alt text is the uploaded filename. Accessibility-oriented alt-text editing can be expanded later without changing the underlying attachment-ID relationship.

## Deletion and Revision Retention

Attachment bytes must not disappear while recoverable note content still references them.

Milestone 0 therefore refuses attachment deletion with HTTP `409` when the attachment UUID is referenced by either:

- the current note document; or
- any retained immutable revision for that note.

This is intentionally stricter than ordinary attachment cleanup. Revision history is currently retained and individual revision deletion is not exposed, so an image referenced by retained history may need to remain stored even after it is removed from the current document.

A future retention policy may introduce safe reference-aware garbage collection, but it must not invalidate recoverable history or silently produce broken restored notes.

## Revision Restore

Revision restore revalidates the historical document before replacing current content. An incompatible document schema returns a conflict rather than being rewritten. If a historical inline-image reference no longer resolves to an approved attachment, restoration fails rather than restoring a knowingly broken document.

This makes attachment preservation part of revision recoverability rather than an unrelated file-management concern.

## Search and Plain-Text Representation

Inline images do not cause binary image data to enter PostgreSQL full-text search. The native plain-text representation uses the image alt text when available, such as `[Image: Network architecture diagram]`, and otherwise records `[Image]`.

OCR remains a future capability and is not implied by inline-image support.

## Export and Migration Requirements

A portable GoreeCloud Notes export must preserve both sides of the relationship:

- note documents containing stable attachment UUID references; and
- the corresponding attachment metadata and binary payloads.

Import validation must prove that every inline attachment reference resolves after migration. Counts alone are not sufficient; checksums, sizes, ownership, note relationships, media types, and document references must be validated.

The transitional Memos JSON export is not sufficient by itself because its attachment metadata does not include attachment binary payloads. The eventual Memos importer must inventory and copy the source attachment bytes directly before the transitional environment can be retired.

## Deferred Production Gates

The following remain deliberately outside the completed Milestone 0 inline-image path:

- SVG sanitization and preview;
- PDF and office-document preview;
- arbitrary external image embedding;
- OCR;
- malware scanning and quarantine policy;
- resumable or multipart large-object upload;
- final production filesystem/object-storage design;
- production storage quotas;
- reference-aware garbage collection after revision-retention policy is approved;
- production backup/restore validation for attachment bytes;
- migration dry runs against isolated transitional Memos data.

These capabilities require separate security, recovery, migration, and operational approval rather than being enabled implicitly by browser image support.
